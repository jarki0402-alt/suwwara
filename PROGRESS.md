# Progress — Suwwara

Log status pembangunan aplikasi. Diperbarui setiap ada perubahan signifikan (fitur baru, bug fix, keputusan arsitektur). Lihat [README.md](./README.md) untuk cara menjalankan proyek.

## Ringkasan status

Aplikasi sudah punya alur inti lengkap: cari lagu → putar → antrean/shuffle/repeat → lirik tersinkron → simpan ke koleksi → dengar offline (cache). Backend sendiri (bukan API musik pihak ketiga) yang meresolusi audio dari YouTube via `yt-dlp`.

**Belum production-ready** — belum ada autentikasi/multi-user, backend masih single-process tanpa persistent database (cache in-memory), dan beberapa perilaku audio di HP (lihat "Known issues") masih perlu diverifikasi langsung di perangkat asli.

## Selesai

- **Playback inti**: AudioEngine berbasis Web Audio API, dua jalur `<audio>` paralel untuk crossfade antar lagu, resolusi bitrate high/low (Data Saver). Auto-lanjut ke lagu berikutnya dipicu langsung dari perbandingan `currentTime` vs durasi asli metadata lagu (bukan nunggu event `'ended'` milik browser) — perlu karena WebKit iOS terbukti bisa salah menghitung durasi file audio streaming progresif sendiri (dikonfirmasi langsung di device: satu kasus persis 2× lipat), jadi `'ended'` gak bisa diandalkan buat nentuin kapan lagu beneran selesai. Watchdog tambahan buat kegagalan lain yang genuinely beda: macet di TENGAH lagu (`STALL_GRACE_MS`), AudioContext mati suri (`SILENT_PLAYBACK_GRACE_MS`), atau gagal dimuat total (network/backend error, dibatasi 3x beruntun biar gak nge-skip seluruh antrean kalau internet mati total). Kalau elemen `<audio>` baru gagal `.play()` pas crossfade, elemen lama sekarang dipaksa berhenti juga — sebelumnya bisa nyangkut dua lagu kedengeran bareng.
- **Antrean**: shuffle, repeat (off/all/one), next/previous, auto-lanjut ke rekomendasi saat antrean habis, drag-to-reorder per baris, tambah ke playlist langsung dari antrean, menu opsi (sukai/putar berikutnya/hapus). Tampilan "Antrean Putar" cuma nampilin lagu yang sedang main + yang belum diputar — lagu yang sudah lewat otomatis hilang dari daftar, lagu yang sedang main selalu jadi baris paling atas (bukan nampilin seluruh histori antrean dari awal).
- **Now Playing**: seek bar dengan thumb drag-to-seek, lirik tersinkron (LRCLIB + parser LRC sendiri, sync sepenuhnya otomatis lewat `frameTicker` bersama yang dipakai fitur lain juga — dibatasi 30fps dan berhenti total kalau tab disembunyikan, jadi gak membebani device), kontrol volume. Panel lirik selalu mulai dari baris paling atas begitu ganti lagu (gak lagi kebawa posisi scroll lagu sebelumnya).
- **Koleksi**: lagu disukai, playlist, riwayat putar, "baru diputar".
- **Rekomendasi & trending**: mesin rekomendasi lokal berbasis histori putar.
- **Pencarian**: hasil dari backend (ytmusic-api/youtube-sr), autocomplete saat mengetik, pencarian terakhir (client-side), grid jelajahi genre/mood (12 kategori, tap → hasil beneran dari backend).
- **Trending global**: dicampur dari shelf kurasi asli YouTube Music (`getHomeSections`, diperbarui YouTube sendiri) + query cadangan, bukan cuma query statis.
- **Radio otomatis**: klik satu lagu dari mana pun (pencarian, trending, rekomendasi, "baru diputar") langsung ngisi antrean pakai lagu-lagu yang beneran mirip (sinyal "up next radio" YT Music, blend 2-3 seed, hanya kandidat yang benar-benar terkait sama lagu yang lagi diputar yang lolos — lihat entri 2026-09-05 soal coherence filter), bukan cuma sisa list yang gak nyambung dan bukan campur genre/bahasa yang gak nyambung satu sama lain. Antrean juga terus nambah sendiri di background begitu mepet ujung — gak pernah beneran berhenti kering kayak streaming musik pada umumnya. Gak ada lagu dobel di antrean (satu lock in-flight yang di-share semua jalur nambah-antrean), dan lagu yang baru diputar gak bakal disaranin lagi selama 3 jam (cooldown berbasis riwayat putar) biar gak berasa muter di lagu yang itu-itu saja.
- **Desktop**: kontrol transport (prev/play/next) di tengah bottom bar persis gaya Spotify, Now Playing jadi tampilan fullscreen (bukan popup kecil).
- **PWA**: installable, service worker (Workbox, `injectManifest`), cache gambar/API dengan strategi berbeda per jenis, prompt update, indikator status offline, estimasi storage. Audio SENGAJA gak di-cache lewat Service Worker (dicabut 2026-09-05) — selalu langsung ke network/backend, gak ada lapisan cache yang bisa jadi basi/rusak di antaranya.
- **Media Session API**: metadata lock-screen, tombol play/pause/next/prev/seek dari lock-screen atau notification bar. Status play/pause di lock-screen gak lagi kedip ke "paused" tiap kali ganti/skip lagu (loading dihitung sebagai "playing" buat keperluan ikon lock-screen). Kedua elemen `<audio>` di-"prime" (di-play+pause sekali, aman terhadap race sama load asli — lihat entri 2026-09-05) pas `unlock()` pertama kali — tanpa ini iOS Safari bisa nolak `.play()` dari action handler lock-screen (next/previous), yang kelihatan kayak "tombol lock-screen gak ngapa-ngapain". Cuma pakai handler `previoustrack`/`nexttrack` (bukan `seekforward`/`seekbackward` — sempat dicoba, ternyata bikin regresi di device asli user, sudah dibalik).
- **Backend**: proxy audio dengan dukungan Range request (untuk seeking), resolusi audio di-cache per video ID, prefetch lagu berikutnya di background. Kalau upstream (googlevideo.com) gak menghormati `Range` yang diminta dan malah balikin file penuh, backend deteksi mismatch itu dan potong sendiri bagian yang bener buat client (lihat entri 2026-09-05) — mencegah client salah kira masih ada konten baru padahal lagu udah abis.
- **Containerized**: `Dockerfile` (frontend, nginx:alpine, ~69MB) + `server/Dockerfile` (backend, node:22-alpine + python3/yt-dlp, ~299MB) + `docker-compose.yml`. Diverifikasi end-to-end (build, health check, search, resolve+stream audio asli lewat yt-dlp di dalam container, render UI lewat browser) — lihat entri di bawah.
- **Tema terang/gelap manual**: bisa dipilih di Pengaturan (Sistem/Terang/Gelap), bukan cuma ikut `prefers-color-scheme` OS. Lihat `useThemeSync`, `theme.css`, `settingsStore.ts`.

## Perubahan terbaru — 2026-09-05 (AKHIRNYA ketemu akar masalah sebenarnya, dibuktikan langsung dari device asli — iOS WebKit salah hitung durasi file, bukan bug jaringan/cache)

Panel diagnostik dari entri sebelumnya berhasil — user kirim screenshot dari iPhone-nya SENDIRI pas bug lagi kejadian, dan datanya jelas banget: `song.duration: 178.00` (metadata benar) vs `element.duration: 355.94` — **persis 2× lipat** (178×2=356). Dikonfirmasi ulang lewat Playwright: LAGU YANG SAMA PERSIS (video ID sama, backend sama) dites di desktop Chromium, hasilnya `177.98` — BENAR, sesuai metadata, gak ada penggandaan sama sekali.

**Kesimpulan yang akhirnya solid**: ini BUKAN bug jaringan, BUKAN bug cache, BUKAN bug backend Range — ini **WebKit di iOS yang salah menghitung durasi FILE-nya sendiri** buat audio yang di-stream progresif (MP4/M4A lewat Range request) — satu kasus yang diukur langsung persis 2× lipat dari yang seharusnya. `'ended'` cuma nyala kalau WebKit SENDIRI merasa udah nyampe akhir — dan karena hitungan durasinya sendiri salah (mikir file-nya 356 detik, padahal 178), dia nunggu sampai 356 detik "versinya sendiri" dulu baru mau kasih sinyal selesai, padahal audio aslinya (dan suaranya) udah abis di 178 detik.

**Ini juga menjelaskan kenapa fix-fix sebelumnya cuma nge-tambal, bukan nyelesein**: `getDuration()` self-correcting (biar duration ikut naik kalau currentTime lewat) itu JUSTRU nutupin gejala aslinya alih-alih ngasih tau ada yang salah — bikin garis waktu ikut "percaya" sama hitungan WebKit yang keliru. Watchdog overrun 120 detik itu nunggu KELAMAAN buat kasus yang beneran cuma butuh nunggu ~178 detik ekstra (durasi asli lagi) sebelum WebKit "nyerah" sendiri.

**Fix yang beneran nutup akar masalahnya**:
1. `AudioEngine.getDuration()` dibalik LAGI ke versi paling simpel — cuma metadata (`song.duration`), TANPA self-correction sama sekali. Biar garis waktu gak ikut "percaya" sama hitungan WebKit yang bisa salah.
2. **Pengecekan completion yang PALING UTAMA sekarang**: `usePlaybackController.ts` langsung bandingin `currentTime >= song.duration` (metadata, yang udah terverifikasi akurat) — begitu nyampe situ, LANGSUNG dianggap selesai dan lanjut ke lagu berikutnya, TANPA nunggu event `'ended'` atau watchdog apapun. Reaksinya dalam hitungan 1 siklus polling (≤2 detik), bukan nunggu WebKit "setuju" dulu yang bisa molor sampai berkali-kali lipat durasi asli lagu.
3. Watchdog `OVERRUN_GRACE_SEC` (120 detik) yang berbasis dugaan yang ternyata salah dihapus total — sudah gak relevan lagi begitu pengecekan langsung ke metadata jadi yang utama.
4. `SeekBar.tsx` dikasih clamp ekstra (`Math.min`) biar SECARA VISUAL gak pernah nunjukin current > total, bahkan di jendela singkat 1 siklus polling sebelum lagu pindah.

Watchdog `STALL_GRACE_MS` (macet TENGAH lagu, sebelum nyampe durasi) dan `SILENT_PLAYBACK_GRACE_MS` (AudioContext mati suri) tetap dipertahankan — dua-duanya nangkep kegagalan yang GENUININE beda (macet SEBELUM pernah nyampe durasi asli), bukan kasus yang baru ditemukan ini.

Diverifikasi lewat Playwright — reproduksi PERSIS skenario yang dilaporkan: metadata bilang 10 detik, file asli beneran 40 detik (4×). Hasilnya: (1) seek bar TETAP nunjukin "0:10" yang benar sepanjang playback (gak pernah ikut ke 40), (2) current time gak pernah kelihatan lewatin total di layar, (3) app otomatis pindah ke lagu berikutnya di detik ~9 (pas currentTime nyampe 10), BUKAN nunggu sampai detik 40. Panel diagnostik (`PlaybackDebugOverlay`, `AudioEngine.getDebugSnapshot()`) sudah dihapus total setelah tujuannya tercapai — gak perlu lagi karena akar masalahnya udah ketemu dan diperbaiki. `tsc -b` dan `npm run test` (23 test) tetap bersih. Docker sudah di-rebuild dan sehat.

## Perubahan terbaru — 2026-09-05 (cache audio di Service Worker dicabut total — akar masalah yang beneran gak abis-abis)

Fix rename cache (`audio-cache` → `audio-cache-v2`) di entri sebelumnya cuma nolong SEKALI — user laporkan lagu BERIKUTNYA kena bug yang sama lagi (garis waktu tembus durasi). Ini nunjukin bukan cuma soal SATU cache lama yang keracunan (itu udah kebersihin), tapi ADA MEKANISME yang bisa bikin masalah baru berulang kali, buat lagu manapun.

**Diskusi sama user dulu sebelum ambil keputusan**: dijelasin apa sebenarnya fungsi cache audio ini (bukan precache — baru nyimpen SETELAH lagu diputar sekali, buat mempercepat REPLAY lagu yang sama / mode offline, BUKAN buat mempercepat lagu BARU yang belum pernah diputar). Mengingat radio queue app ini sengaja didesain biar lagu gak keulang dalam 3 jam (cooldown), manfaat cache ini buat pola pakai app ini kecil — sementara biayanya (bug berulang, susah di-debug tuntas) udah kebukti besar lewat beberapa sesi debugging. User setuju: **cache audio dicabut total**, prioritas ke stabilitas/pengalaman kayak Spotify Premium ketimbang fitur offline yang marginal.

**Kemungkinan penyebab kambuh berulang**: caching sebuah respons yang lagi di-STREAM (bukan file utuh yang udah selesai) itu beresiko — kalau koneksi kepotong di tengah jalan (jaringan lambat, apalagi lewat Cloudflare Tunnel yang keterbatasan upload-nya udah dibahas), hasilnya cache yang KEPOTONG/gak lengkap buat lagu ITU, dan `RangeRequestsPlugin` gak bisa motong dengan aman dari cache yang gak lengkap begitu. Ini bisa kejadian di LAGU MANAPUN, kapan aja — bukan cuma sekali, cocok sama laporan "sekali doang normal, abis itu kambuh lagi di lagu lain".

**Fix**: route `CacheFirst` + `RangeRequestsPlugin` buat audio di `src/sw.ts` dihapus SELURUHNYA (bukan cuma di-rename lagi). Semua request `/api/audio/*` sekarang gak disentuh Service Worker sama sekali — langsung ke network/backend setiap saat, gak ada lapisan cache apapun di antaranya yang bisa jadi basi/rusak. Dependency `workbox-range-requests` yang jadi nganggur ikut dibuang dari `package.json`.

Diverifikasi: build produksi dicek langsung — gak ada lagi jejak `audio-cache` atau route berbasis `destination==='audio'` di `sw.js` yang di-build. Request audio dengan `Range` header tetap dites lewat backend asli + video YouTube sungguhan, hasilnya tetap `206 Partial Content` dengan ukuran yang benar (fix backend dari entri sebelumnya tetap jadi satu-satunya, dan sekarang satu-satunya, lapisan yang menjaga kebenaran Range response). `tsc -b`, `npm run test` (23 test), dan `npm run build` (full production build) semuanya bersih.

## Perubahan terbaru — 2026-09-05 (akhirnya ketemu akar masalah SEBENARNYA: bug di backend proxy audio, bukan di AudioContext)

Fix `isAudioSilentWhilePlaying()` di entri sebelumnya ternyata BELUM cukup — user laporkan lagi persis kasus yang sama ("Espresso" - Sabrina Carpenter, harusnya selesai 2:56, garis waktu kiri-kanan malah tembus sampai 3 menit bahkan 5 menit, sinkron identik, suara BENERAN stop). Petunjuk paling penting kali ini: **kejadian di Android DAN iPhone, tapi AMAN di desktop**. Ini nge-eliminasi teori bug WebKit (Android Chrome gak punya bug itu) dan ngarahin ke sesuatu yang common di HP tapi enggak di desktop — kemungkinan besar soal POLA REQUEST, bukan soal engine JS.

**Akar masalah asli, akhirnya ketemu di BACKEND**: browser mobile bikin BANYAK request `Range` kecil-kecil sepanjang lagu diputar (buat hemat data/baterai), beda dari desktop yang cenderung download borongan di awal. Backend kita (`server/src/routes/audio.ts`) selama ini nge-relay respons dari server YouTube (googlevideo.com) APA ADANYA tanpa validasi — kalau upstream-nya kebetulan GAK menghormati header `Range` yang diminta dan malah ngirim balik SELURUH FILE dari awal (status 200, bukan 206 partial) — yang ternyata BISA KEJADIAN, terutama buat request Range yang jatuh di posisi tertentu — client (elemen `<audio>` di HP) nerima data yang dikiranya "konten baru" di posisi yang diminta, padahal itu PENGULANGAN dari awal file. Ini bikin `currentTime` terus "maju" (karena beneran ada byte baru yang di-decode), tapi begitu sampai ke bagian yang gak sinkron sama posisi playback asli, hasilnya diem/gak ada suara — persis "suara stop tapi garis waktu jalan terus".

**Fix**: backend sekarang DETEKSI mismatch ini — kalau kita minta `Range` tertentu tapi upstream balikin 200 (bukan 206), backend BUFFER seluruh respons SEKALI, lalu potong sendiri byte yang beneran diminta client, dan kirim balik sebagai `206 Partial Content` yang benar. Hasil buffer di-cache per video+kualitas biar chunk-chunk berikutnya dari HP yang sama gak perlu download ulang seluruh file tiap kali (cukup potong dari buffer yang udah ada). Kalau client minta byte yang BENERAN udah lewat ujung file asli, sekarang dijawab `416 Range Not Satisfiable` yang benar (bukan ngirim ulang isi dari awal file yang bikin bingung).

Diverifikasi lewat script terpisah yang bikin server "upstream" palsu yang sengaja ABAIKAN Range (reproduksi persis bug-nya), dites lewat proxy asli — dikonfirmasi: (1) potongan byte yang dikembalikan selalu PERSIS benar buat berbagai posisi Range, (2) request yang minta byte melewati akhir file asli dengan benar dapat `416` (bukan data duplikat), dan (3) upstream cuma di-fetch SEKALI biarpun ada beberapa request chunk berurutan (cache buffer jalan). Smoke test tambahan ke backend asli + video YouTube sungguhan mengonfirmasi request Range normal (skenario paling umum) tetap jalan benar, gak ada regresi. `tsc` bersih di backend maupun frontend. Docker di-rebuild (backend-nya — sempat ketauan `docker compose up -d --build` gak otomatis recreate container backend walau image-nya berubah, harus pakai `--force-recreate` secara eksplisit — dicatat sebagai catatan operasional buat sesi berikutnya).

## Perubahan terbaru — 2026-09-05 (seek bar lanjut jalan padahal suara udah beneran stop, gak next — ketemu akar masalah baru: AudioContext "mati suri")

User laporkan lagi (di PWA HP): lagu seharusnya selesai di 2:30, tapi garis waktu (angka kiri DAN kanan, dua-duanya) bisa lanjut jalan sampai 3 menit — sinkron satu sama lain, tapi suaranya SUDAH BENERAN BERHENTI (bukan cuma kedengeran diam, beneran stop). Dan gak pernah lanjut ke lagu berikutnya.

**Akar masalah baru, beda dari yang udah di-fix sebelumnya**: watchdog "overrun" dari entri sebelumnya emang ada, tapi ambang batasnya sengaja digenerin 120 detik (2 menit) biar gak salah motong lagu yang metadata-nya cuma meleset wajar. Kasus ini cuma ~30 detik lewat durasi — jauh di bawah ambang batas itu, jadi belum sempat kepicu, user ngerasa "gak next-next" padahal sebenarnya cuma belum nyampe waktunya.

Tapi ini nunjukin ada kasus LAIN yang lebih spesifik dan lebih cepat harus ditangani: kalau **suara BENERAN berhenti** (bukan cuma lambat), padahal `currentTime` masih jalan terus — itu tandanya `AudioContext` (jalur Web Audio yang nyambung ke speaker) "mati suri" sementara elemen `<audio>` di baliknya tetap jalan sendiri ngitung waktu, gak peduli suaranya beneran keluar atau enggak. Ini persis pola bug WebKit yang udah ditemukan di entri sebelumnya (`bugs.webkit.org` #263627) — `AudioContext` bisa nyangkut di status `'interrupted'`/suspended, dan `resume()` yang biasanya kita panggil buat benerin itu **diam-diam gak pernah beneran berhasil** di kasus tertentu.

**Fix**: method baru `AudioEngine.isAudioSilentWhilePlaying()` — true kalau status kita bilang `'playing'` tapi `AudioContext`-nya beneran gak `'running'`. Watchdog baru di `usePlaybackController.ts` mantau ini, dan kalau kondisi itu bertahan 8 detik (`SILENT_PLAYBACK_GRACE_MS`) — jauh lebih cepat dari 120 detik punya overrun watchdog, karena di sini kita udah TAU suaranya gak bakal balik (beda dari kasus "mungkin cuma lagu panjang") — dipaksa lanjut ke lagu berikutnya.

Diverifikasi lewat Playwright dengan cara yang paling meyakinkan: bukan simulasi palsu, tapi BENERAN manggil `AudioContext.suspend()` asli pada context yang lagi dipakai app, sambil nge-patch `resume()`-nya biar SELALU gagal diam-diam (persis reproduksi bug WebKit-nya) — dikonfirmasi watchdog baru berhasil deteksi kondisi ini dan otomatis lanjut ke lagu berikutnya sekitar 8 detik kemudian, tanpa perlu nunggu 120 detik. `npm run test` (23 test) dan `tsc -b` tetap bersih. Docker sudah di-rebuild dan sehat.

## Perubahan terbaru — 2026-09-05 (antrean radio kadang isinya lagu dobel + cooldown biar gak muter di lagu yang itu2 aja)

User bilang algoritma radio-nya (kesamaan genre/mood) sudah cocok, cuma minta dua hal: (1) lagu yang sudah ada di antrean jangan sampai dimasukkan lagi jadi dobel, dan (2) lagu yang baru diputar boleh muncul lagi tapi baru sekitar 2-3 jam kemudian, biar gak berasa muter di lagu yang itu-itu saja.

**Bug nyata ditemukan lewat testing, bukan cuma dari laporan**: dicoba klik lagu dari hasil pencarian lewat browser beneran, terus dicek isi antrean-nya (`localStorage['suwwara-queue']`) — ternyata BENERAN dobel: dari 25 lagu di antrean cuma 13 yang unik, 12 sisanya adalah lagu yang sama muncul dua kali.

**Akar masalah (race condition)**: `playSongRadio()` (dipanggil pas user klik lagu dari pencarian/trending/rekomendasi) langsung nge-build radio queue sendiri dari lagu yang baru diklik. Tapi PAS BERSAMAAN, efek proaktif nambah-antrean di `usePlaybackController.ts` (yang tugasnya nge-topup antrean begitu sisa lagu di depan tinggal ≤3) JUGA ikut kepicu — soalnya antrean baru aja di-reset jadi cuma 1 lagu (sisa 0 di depan, di bawah ambang batas topup). Dua-duanya jalan hampir bersamaan, dari seed yang SAMA persis, dan dua-duanya SAMA SEKALI GAK TAU kalau yang satu lagi juga lagi nge-fetch "lagu mirip" buat seed yang sama — begitu dua-duanya selesai, kandidat yang sama ikut ditambahkan ke antrean dari kedua jalur itu, jadi dobel. Ini murni race condition, bukan soal algoritma kesamaan lagunya (yang memang sudah bagus, sesuai kata user).

Ada race KEDUA yang mirip: efek proaktif topup dan jalur fallback "antrean beneran habis" (dipicu pas lagu kelar diputar tapi topup belum sempat selesai) juga bisa jalan bersamaan tanpa saling tahu satu sama lain — potensi dobel yang sama.

**Fix race condition**: satu lock module-level (`queueExtensionInFlight` di `playSongRadio.ts`) yang di-share oleh SEMUA jalur yang bisa nambah antrean radio (klik lagu baru, topup proaktif, fallback antrean-habis) lewat satu fungsi baru `extendQueueWithRadio()`. Siapa pun yang nyoba nambah antrean pas ada proses lain yang masih jalan bakal langsung di-skip (bukan ngerace) — proses yang lagi jalan itu yang bakal nambahin hasilnya begitu selesai. Sebelumnya `usePlaybackController.ts` punya ref lokal sendiri (`isExtendingQueueRef`) yang cuma nyegah race ANTARA dua efek DI DALAM hook itu sendiri — gak nyadar sama sekali kalau `playSongRadio()` di file lain juga bisa mulai proses serupa di waktu yang sama. Sekarang ref lokal itu dihapus total, semua tiga jalur pakai lock yang sama.

**Fix cooldown waktu**: fungsi baru `recentlyPlayedIds(windowMs, history)` di `historyLog.ts` — baca riwayat putar (`loadHistory()`, sudah nyimpen timestamp per lagu) dan balikin Set berisi ID lagu yang diputar dalam `windowMs` terakhir. Dipakai di `buildRadioQueue()` (`playSongRadio.ts`) buat nyaring kandidat, digabung sama pengecualian antrean yang sudah ada — cooldown di-set 3 jam (`REPEAT_COOLDOWN_MS`). Ini penting karena excludeIds yang berbasis antrean doang gak cukup: begitu user klik lagu BARU dari pencarian, antrean di-reset total (`setQueue([song], 0)`) — riwayat "lagu apa aja yang baru diputar di antrean lama" ikut hilang, padahal lagu yang baru aja selesai diputar (lewat radio SEBELUMNYA) harusnya tetap gak muncul lagi buat sementara. Cooldown berbasis waktu (dari riwayat putar yang persisten, bukan dari isi antrean yang sering di-reset) nutup celah ini.

Diverifikasi: (1) unit test baru (`tests/recommendation/historyLog.test.ts`, 4 test) buat `recentlyPlayedIds` — lagu dalam window kepilih, lagu di luar window (lebih dari 3 jam lalu) gak kepilih (jadi bisa muncul lagi), riwayat kosong balikin Set kosong. (2) Fix race condition diverifikasi FUNGSIONAL lewat Playwright — klik lagu asli dari pencarian (backend beneran, bukan mock), baca isi antrean dari localStorage: SEBELUM fix 25 lagu/13 unik (dobel), SESUDAH fix 13 lagu/13 unik (nol dobel). Dicoba juga skenario ganti lagu dengan cepat (klik lagu lain sebelum radio pertama kelar di-build) — tetap nol dobel. `npm run test` (17 test, termasuk 4 baru) dan `tsc -b` tetap bersih.

**Kejujuran soal keterbatasan verifikasi**: cooldown 2-3 jam sendiri gak bisa diverifikasi lewat sesi putar beneran (butuh nunggu 3 jam beneran) — yang diverifikasi cuma logika filtering waktunya lewat unit test dengan timestamp palsu, bukan pengalaman putar-lagu 3 jam yang sesungguhnya. Cukup yakin secara logika (fungsinya murni, gak ada state tersembunyi) tapi belum ada bukti end-to-end jangka panjang.

Diagnosis + fix:

- **Panas & baterai boros — frameTicker dulu berjalan di refresh rate layar, bukan 60fps tetap.** `requestAnimationFrame` mengikuti refresh rate asli layar; di HP 90/120Hz (termasuk banyak iPhone ProMotion), itu berarti visualizer, seek bar, dan lyrics sync semuanya menggambar ulang hingga 120x/detik, dua kali dari yang diasumsikan. Sekarang `frameTicker` (satu-satunya rAF loop bersama yang dipakai semua fitur itu) dibatasi ke maksimum 30 update/detik — turun signifikan tanpa terasa bedanya secara visual untuk bar visualizer atau progress bar. Lihat `src/audio-engine/frameTicker.ts`.
- **`navigator.mediaSession.setPositionState()` sebelumnya dipanggil di setiap frame (berpotensi 60-120x/detik)** — padahal lock-screen scrubber sudah otomatis meng-interpolasi posisi sendiri di antara update. Native bridge call sebesar itu frekuensinya termasuk kerja paling mahal yang dilakukan app tiap frame di HP. Sekarang dibatasi ke 1x/detik (`src/media-session/useMediaSession.ts`).
- **Ganti lagu dari hasil pencarian terasa lambat**: bukan murni soal framework — backend ini meresolusi audio dari YouTube lewat `yt-dlp` per lagu (bisa beberapa detik), beda arsitektur total dari Spotify yang punya CDN musik berlisensi siap pakai. Yang sempat memperlambat lebih jauh: kalau ada dua request untuk lagu+kualitas yang sama nyaris bersamaan (mis. prefetch lagu berikutnya lalu user keburu klik lagu itu juga), backend dulu menjalankan **dua proses `yt-dlp` terpisah** untuk permintaan yang identik. Sekarang di-dedup — request kedua tinggal menunggu hasil yang pertama alih-alih ikut memicu proses baru (`server/src/youtube/stream.ts`). Latensi awal resolusi yt-dlp untuk lagu yang benar-benar baru tetap ada dan memang bawaan arsitektur ini — lihat "Known issues" untuk opsi lanjutannya.
- **Internet jelek → lagu diam loading tanpa error apa pun (bug nyata, sudah diverifikasi)**: `playbackState.error` dari AudioEngine ternyata tidak pernah ditampilkan di UI manapun — kalau `loadTrack` gagal atau timeout (setelah 15 detik menunggu tanpa hasil), status cuma diam-diam balik ke tidak buffering tanpa pesan. Sekarang kegagalan apa pun (koneksi ditolak, timeout, error elemen audio) memicu toast error dengan tombol "Coba lagi". Diuji dengan mensimulasikan koneksi yang macet total (request digantung, tidak pernah selesai) — setelah ~15 detik toast "Koneksi lambat — lagu gagal dimuat." benar-benar muncul dengan tombol retry. Lihat `src/playback/usePlaybackController.ts`.

Juga menambahkan atribut `playsinline`/`webkit-playsinline` dan meta tag `apple-mobile-web-app-capable` di `index.html` untuk perilaku standalone iOS yang lebih benar.

## Perubahan terbaru — 2026-09-05 (fitur Jam — dengerin bareng kolaboratif)

User minta fitur "Jam" mirip Spotify: share link, semua yang gabung jadi peserta **setara** — bisa sama-sama nambah/hapus/atur ulang antrean dan kontrol play/pause/next/back, bukan model host/follower di mana cuma satu device yang berkuasa.

**Arsitektur**: server (Express) sekarang memegang canonical state (antrean + status playback) per room — bukan salah satu device. Semua device kirim *intent* (`add-to-queue`, `remove-from-queue`, `reorder`, `play`, `pause`, `next`, `previous`, `seek`, dst) lewat `POST /api/jam/:roomId/action`, server menerapkannya (reducer murni di `server/src/jam/queueReducer.ts`, port 1:1 dari logika `src/stores/queueStore.ts` — sengaja diduplikasi, bukan di-share lewat build system, karena root pakai ESM/Vite dan `server/` CommonJS), lalu broadcast hasilnya ke SEMUA anggota room (termasuk pengirimnya sendiri, tanpa special-case) lewat **Server-Sent Events** (`GET /api/jam/:roomId/stream`) — dipilih dibanding WebSocket karena app ini 100% REST hari ini, SSE gak butuh ubah `nginx.conf` sama sekali (WS butuh header `Upgrade`/`Connection` yang gak ada di block `/api/` sekarang), dan gak nambah dependency (`ws`/`socket.io` gak dipakai — client pakai `EventSource` bawaan browser). Audio tetap TIDAK direlay antar device — tiap device tetap streaming sendiri dari `/api/audio` yang sudah ada, yang disinkronkan cuma data kecil (posisi, isPlaying, queue).

**Satu-satunya asimetri, murni implementasi bukan hak kontrol**: perluasan queue otomatis (`extendQueueWithRadio`) cuma jalan di device pembuat room ("creator"), biar gak ada beberapa device nambahin lagu filler berbeda barengan — semua device tetap bisa add/remove/reorder/play/pause/skip sama persis.

**Deteksi lagu selesai** tetap jalan lokal di semua device (watchdog yang sudah ada di `usePlaybackController.ts` gak diubah sama sekali), tapi actionnya sekarang kirim intent `advance-on-ended` ke server; server dedupe berdasarkan song-id lagi-diputar biar dua device yang sama-sama trigger di waktu berdekatan gak bikin lagu ke-skip dua kali.

**Bug ditemukan & diperbaiki saat verifikasi nyata (bukan cuma nulis kode terus asumsi jalan)**:
- `AudioEngine.loadTrack()` dengan `autoplay:false` (dipakai jam-mode biar lagu yang baru masuk ke queue kosong gak "kedip" main sebentar lalu pause lagi) ternyata gak pernah nyetel status keluar dari `'loading'` — jadi status macet permanen dan efek sinkron play/pause di Jam gak pernah dapat kesempatan coba `play()`. Ditambal `else` branch yang nyetel status ke `'paused'`.
- **Remote play arriving via SSE gak punya user-gesture** — browser blokir `audioEngine.play()` kalau dipanggil dari efek React yang dipicu event jaringan, bukan dari klik langsung (kelas masalah yang sama dengan yang bikin `unlock()` ada buat MediaSession, tapi di sini gak ada gesture apa pun buat disandarin). Ditambal toast "Ketuk untuk lanjutkan audio Jam." dengan tombol retry yang manggil `play()` langsung di dalam klik itu sendiri.

**File baru**: `server/src/jam/{types,queueReducer,roomManager}.ts`, `server/src/routes/jam.ts`, `src/stores/jamStore.ts`, `src/jam/{jamClient,jamQueueActions,useJamSync,queueSnapshot}.ts`, `src/components/{JamSheet,JoinJamSheet}/`. Entry point: baris "Jam" baru di Pengaturan → Pemutaran, dan link share `?jam=<roomId>` yang otomatis buka prompt gabung saat dibuka.

Diverifikasi lewat Playwright headless (bukan cuma baca kode) jalan lewat **docker-compose beneran** (bukan dev server) di dua browser context terpisah (simulasi 2 device): buat Jam di device A → share link → device B gabung → device B cari lagu asli & nambahin ke antrean → **device A ikut menampilkan & memutar lagu itu secara otomatis** (audio sungguhan lewat yt-dlp, bukan mock) → device B tekan play → **device A ikut mulai main** → device B keluar dari Jam → antrean pribadinya (yang sempat ketiban antrean kosong pas gabung) **kembali utuh**. Nol error console di semua langkah.

## Perubahan terbaru — 2026-09-05 (fix Jam: reload PWA & gabung pakai kode)

User (yang share link, bukan yang gabung) laporkan lagu yang ditambahin gak muncul di device-nya sendiri, padahal muncul di device teman yang baru gabung. **Akar masalah**: `jamStore` cuma nyimpen `clientId` ke localStorage — `role`/`roomId` selalu reset ke `'solo'` tiap kali app di-reload. Di PWA, pindah ke app lain (misalnya WhatsApp buat kirim link Jam) sangat sering memicu OS me-reload tab yang di-background begitu dibuka lagi — sesi Jam pun hilang diam-diam tanpa notifikasi apa pun, tepat di momen orang yang share link itu sendiri paling mungkin ninggalin app. Fix: `role`, `roomId`, `isCreator`, dan `preJamQueueSnapshot` sekarang ikut dipersist (`src/stores/jamStore.ts`) — begitu app dibuka lagi, `useJamSync` otomatis reconnect ke room yang sama tanpa aksi apa pun dari user. Ditambah safety net: kalau room ternyata sudah gak ada lagi di server (berakhir/di-GC selagi device itu pergi), koneksi nyerah setelah 8 detik dan device otomatis balik ke mode solo + queue pribadinya dikembalikan (`ROOM_RECONNECT_TIMEOUT_MS` di `useJamSync.ts`).

User juga menyadari sendiri: buka link share di HP biasanya cuma nyalain browser, bukan app PWA yang sudah ter-install (link-to-app deep linking gak reliable di banyak platform) — jadi link share aja gak cukup. Ditambahkan alternatif **"Gabung pakai kode"**: input 6-karakter di sheet Jam (tampil saat belum ikut Jam) buat masuk pakai kode room secara manual dari dalam app yang sudah kebuka, gak perlu ngandelin link. Logika join di-share lewat `src/jam/joinJam.ts` — satu fungsi yang sama dipakai baik oleh `JoinJamSheet` (dari link) maupun input kode baru di `JamSheet`.

Diverifikasi lewat Playwright: device A bikin Jam → **di-reload paksa** (simulasi PWA ke-kill pas di-background) → device B gabung pakai KODE (bukan link) → device B nambah lagu → **device A yang barusan reload tetap nerima & nampilin lagu itu**, tanpa perlu buka Jam lagi secara manual.

**Follow-up fix (masih 2026-09-05)**: user laporkan lewat Cloudflare Tunnel (laptop ↔ HP), habis buat/gabung Jam gak lama muncul "Room Jam tidak ditemukan lagi" padahal room-nya masih hidup. Penyebabnya: timer "nyerah" di atas (`ROOM_RECONNECT_TIMEOUT_MS`) di-set 8 detik — aman banget di tes localhost/Docker (round-trip milidetik), tapi lewat jalur nyata (Cloudflare Tunnel + data seluler + HP yang baru bangun dari background), koneksi awal bisa lebih lambat dari itu, jadi ke-flag "gak ada" padahal cuma lagi nyambung. Dinaikkan ke 25 detik — ini murni safety-net buat kasus room beneran udah gak ada, bukan pengecekan latensi, jadi aman dibikin longgar.

## Known issues / keterbatasan

- **Bug iOS 26: kemungkinan ada gap/celah kecil di bawah bottom nav saat dibuka sebagai PWA standalone** — sudah diverifikasi ini BUKAN bug dari kode Suwwara (CSS yang di-build sudah dicek langsung dan benar, reservasi `env(safe-area-inset-bottom)` sudah tepat sesuai pedoman Apple). Ini bug platform iOS 26 yang sudah banyak dilaporkan developer PWA lain juga (lihat entri 2026-09-05 buat detail investigasi lengkapnya) — di luar kendali kode web app manapun, cuma bisa diperbaiki lewat update iOS dari Apple.
- **iOS Safari: kemungkinan masih ada glitch suara sangat singkat pas layar dikunci** — akarnya bug WebKit yang masih terbuka (bugs.webkit.org #263627, "AudioContext is not consistently resumed"), bukan sesuatu yang bisa diperbaiki tuntas dari sisi kode web app manapun. Sempat dicoba di-debounce (nunggu 400ms sebelum resume) tapi itu malah bikin regresi lebih parah (jeda ~1 detik yang jelas kerasa, dibanding klik sepersekian detik) — sudah dibalik ke resume langsung tanpa delay (lihat entri 2026-09-05), jadi klik singkat ini kemungkinan tetap ada tapi itu pilihan yang lebih baik dibanding alternatifnya.
- **Latensi ganti lagu tidak akan pernah menyamai Spotify** selama backend meresolusi audio dari YouTube lewat `yt-dlp` per request alih-alih CDN musik berlisensi — ini keputusan arsitektur dasar proyek (lihat komentar di `server/src/youtube/stream.ts`), bukan sesuatu yang bisa dioptimasi hilang sepenuhnya. Mitigasi yang sudah ada: prefetch resolusi untuk lagu *berikutnya* di antrean saat lagu sekarang masih main (`prefetchAudio` di `usePlaybackController.ts`) dan dedup request identik (lihat di atas). Belum ada: prefetch untuk hasil pencarian yang baru terlihat/disentuh (bisa mempercepat lompat ke lagu baru, tapi menambah beban `yt-dlp` di backend untuk lagu yang belum tentu jadi diputar — trade-off yang belum diputuskan).
- **Toast error kadang muncul dobel** untuk satu kegagalan (native audio-element error, bukan timeout) — AudioEngine punya jalur error internal sendiri (mid-playback failure) terpisah dari jalur `loadTrack`/`crossfadeTo` yang di-catch di `usePlaybackController`, dan keduanya bisa sama-sama menulis ke `usePlayerStore.error` untuk kegagalan yang sama saat loading awal. Bukan bug fungsional (pesannya tetap benar & masuk akal, cuma tampil dua kali berurutan), tapi belum di-dedup dengan rapi.
- **Menutup PWA sepenuhnya (swipe-close dari app switcher) akan menghentikan audio** — ini bukan bug yang bisa diperbaiki dari sisi web app: menutup app sama dengan mematikan proses JavaScript-nya, sama seperti yang terjadi di semua pemutar musik berbasis web/PWA lain (termasuk Spotify Web, YouTube Music PWA, dll). Untuk audio yang tetap jalan setelah app benar-benar ditutup, satu-satunya jalan adalah aplikasi native (Android/iOS) dengan foreground service — di luar cakupan PWA. Yang *bisa* dan sudah diperbaiki: audio tetap jalan saat layar dikunci selama app masih berjalan di background (lihat perubahan di atas).
- ~~Fix DOM-attachment untuk audio silence di iPhone standalone belum dikonfirmasi~~ → **dikonfirmasi user, sudah bekerja di iPhone (Home Screen app) sejak sesi 2026-09-04.**
- `devOptions.enabled: false` di `vite.config.ts` berarti service worker & manifest PWA **tidak aktif saat `npm run dev`** — hanya aktif di hasil `npm run build` (termasuk lewat Docker, karena `Dockerfile` frontend menjalankan `npm run build` juga).
- Backend meng-cache hasil resolusi audio in-memory (lihat `server/src/youtube/stream.ts`) — hilang setiap restart/redeploy container, belum ada persistent store. Kalau nanti pola pakai makin sering (banyak restart/redeploy), pertimbangkan Redis buat cache ini biar gak hilang tiap deploy ulang — sempat didiskusikan tapi belum dieksekusi.
- **State room Jam juga in-memory** (`server/src/jam/roomManager.ts`) — sama seperti cache audio di atas, hilang kalau backend restart/redeploy (room aktif otomatis bubar, member perlu bikin/gabung ulang). Wajar untuk skala circle kecil ini, belum perlu persistent store.
- **Sinkronisasi posisi antar device di Jam sengaja "cukup baik", bukan presisi sample-accurate** — toleransi drift ~1.5 detik sebelum device melakukan koreksi seek, karena tidak ada mekanisme sinkronisasi clock Web Audio antar device (tiap `AudioContext` cuma tahu waktunya sendiri). Cukup buat dengerin bareng santai, bukan buat kebutuhan yang butuh presisi milidetik.
- Belum ada test coverage untuk AudioEngine, MediaSession, atau komponen UI (ProgressBar, PlayerControls) — test yang ada baru untuk bitrate resolver, parser LRC, dan scoring rekomendasi.
- **Rencana hosting**: satu VPS (Oracle Cloud Always Free) menjalankan kedua container (`docker compose up -d`), bukan Vercel — backend butuh proses persisten + `yt-dlp`/Python yang gak cocok sama model serverless Vercel. Cloudflare (Tunnel atau proxy DNS) direncanakan di depan buat domain+HTTPS, dengan audio streaming kemungkinan di-bypass dari proxy Cloudflare (pakai `docker-compose.yml`'s exposed `8787:8787`) untuk menghindari batasan ToS Cloudflare soal trafik audio/video yang "gak proporsional". Belum di-deploy ke VPS beneran — baru diverifikasi jalan penuh secara lokal via Docker.
